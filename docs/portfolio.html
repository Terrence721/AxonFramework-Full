A deliberate Maven→Gradle build migration — early stage, honestly reported

This isn't a finished modernization with metrics to brag about — it's six days into a build-system migration of Axon Framework 5, converted one file at a time rather than run through an automated tool. What's below is exactly where that stands: what's real, what isn't yet, and the handful of genuine mistakes and corrections along the way — not smoothed over.

Why file-by-file, not a converter

Pointing a Maven→Gradle conversion tool at this reactor and committing whatever comes out would be faster. It would also miss everything interesting: Gradle has no equivalent of Maven's parent-POM inheritance, so a shared dependency that's harmless in axon-parent becomes a literal circular dependency the moment a tool mechanically applies it to the one module that dependency points at. A checkstyle rule copied byte-for-byte looks complete right up until you read the comment sitting three lines above it. Every module in this reactor gets read, not just copied — and that reading is where the actual engineering happens.

Real findings, not asserted ones

Real bug

A circular dependency Gradle would happily let you create

The shared testImplementation(project(":test-logging")) line in the base convention plugin would make test-logging depend on itself the moment it applied that same plugin — upstream's Maven POM dodges this with a parent-inheritance trick Gradle doesn't have an equivalent of. Guarded with a one-line if (project.name != "test-logging") and verified with a real gradle :test-logging:dependencies run showing no self-reference, not just reasoned about.

Real bug

An undocumented Gradle 9.2 / nmcp interaction bug

Central Portal publishing config using providers.environmentVariable(...) for credentials crashes Gradle's configuration cache with a serialization error — reproduced directly, nothing about it findable publicly at the time. Fixed with a plain System.getenv(...) read instead.

Real bug

A directory that was both real content and Gradle's own output folder

The root build/ directory does double duty — a real, intentionally-tracked module directory and Gradle's default build-output location for the root project. A blanket .gitignore exception meant to protect the former was quietly leaking the latter's Gradle-generated reports as trackable files. Replaced with an explicit allow-list of just the real paths.

Real bug

Gradle refusing to configure the entire build over one missing folder

Every include(...) in settings.gradle.kts pointed at a module directory that didn't exist yet, which made Gradle refuse to evaluate the build at all — not just skip the missing module. Fixed by commenting each include out individually, brought back one at a time as each module is actually converted.

Real bug

Dead references in upstream's own Maven config

Root pom.xml's Javadoc-skip list names four modules — axon-todo, axon-legacy, axon-legacy-aggregate, axon-legacy-saga — that don't exist anywhere in this reactor. Looks like uncleaned drift from an Axon 4-era POM. Not carried forward.

Getting it wrong once, and what that's worth reporting

Self-correction
First pass on build/checkstyle.xml: flagged its nullness-annotation ban list as inconsistent because Spring's @Nullable wasn't banned alongside @NonNull. Wrong — a comment three lines above the rule already explained the omission was deliberate, deferred until the project is "SpringBoot 4 native." Caught on a second read before the change was made, corrected, and the reasoning kept — including the fact that the correction happened, not just the fixed version.

What hasn't started yet

No padding here — this is a build-system migration with almost the whole reactor still ahead of it:

  • 13 of 14 reactor modules are still Maven-only — no Axon Framework Java/Kotlin source has been converted
  • No tests exist in this repo yet — nothing to report a pass rate on
  • No CI workflow yet (tracked, scoped minimal, not started)
  • No Gradle wrapper generated yet — building requires a system-installed Gradle
  • Nothing has ever been published to Maven Central — the pipeline is wired, unexercised
